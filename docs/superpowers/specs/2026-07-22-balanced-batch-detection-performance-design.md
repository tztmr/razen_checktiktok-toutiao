# 批量检测平衡性能优化设计

## 背景与目标

当前批量检测会根据 CPU 数启动 4–20 个包级 worker。单个抖音包内部依次执行本地参数提取、账号提取、两个 Token 接口、身份补全、密码检查和实名检查；联网请求的统一超时为 15 秒。200 多个包同时检测时，高包级并发、重复 ZIP 扫描和单包串行等待会相互放大，形成 60–200 秒的长尾。

本次采用平衡模式：不缩短 15 秒请求超时，不以增加请求失败或掉线误判换取速度。通过限制包级并发、并行同包独立检查、复用单行提取结果、缓存非敏感 ZIP 索引并记录分步耗时，降低普通包和整批任务的等待时间。

## 成功标准

- 包级并发稳定在 6–8 路，不再达到 20 路。
- 抖音 Token、密码和实名等互不依赖的检查并行启动。
- 头条 Token 与实名检查并行启动。
- 同一检测行不重复调用账号凭据提取。
- 多账号包同时最多处理两个非当前账号。
- ZIP 文件位置缓存按源路径和修改时间自动失效。
- 网络请求继续使用 15 秒超时；请求失败不被标记为确认掉线。
- 检测结果保留总耗时，并能查看、导出分步骤耗时。
- 用可控延时测试证明独立步骤耗时接近最长步骤，而不是所有步骤相加。

性能目标是普通抖音包约 15–30 秒；需要身份补全或网络持续超时时可能约 30–45 秒。这是目标范围，不是对外部接口延迟的硬性保证。

## 调度策略

新增纯函数根据 CPU 核心数和包数计算 worker 数：

- 没有包时返回 0。
- 包数少于 6 时，worker 数不超过包数。
- 其他情况最低 6 路、最高 8 路。
- CPU 核心数在 6–8 之间时直接使用该数量；更低按 6 路、更高按 8 路处理。

停止检测仍采用现有语义：不再领取新包，已经发出的请求等待返回，不强行中断后台请求。

## 单包执行阶段

### 抖音

抖音检测分成以下阶段：

1. 本地准备：`extract_douyin_request_params` 与 `extract_douyin_account_credentials` 并行执行。
2. 当前账号检查：根据选项并行执行 Token、密码和实名（证书）检查。
3. 身份补全：这是与实名检查不同的后置步骤，只在 Token 检查结束、已有 `secUid` 且 UID 或 UniqueId 缺失时调用。
4. 多账号检查：复用第一阶段取得的账号凭据，不再重复提取；非当前账号同时最多处理两个。每个账号的 Token 与密码检查互不依赖时并行执行。
5. 合并：沿用当前在线、掉线、失败和功能状态的合并规则。

单个步骤失败不会取消同阶段的其他步骤。使用等价于 `Promise.allSettled` 的结果收集方式，分别保留成功结果和错误信息。

### 今日头条

头条 Token 与实名检查互不依赖，按照已勾选选项并行执行。两项均未勾选时不发送请求。在线信号、掉线信号和请求错误继续按照现有规则合并，不改变业务判定。

## 缓存边界

### 跨命令缓存

后端新增 ZIP 文件位置索引缓存，用源 ZIP 路径、修改时间和 APP ID 作为缓存键。首次查找时扫描 ZIP 目录并记录可分析文件位置，后续检测命令直接查询索引。ZIP 修改后缓存键改变，旧结果不会复用。备份目录继续走现有实时查找流程，不使用此 ZIP 缓存，避免目录内部文件变化未反映到目录修改时间时读到旧索引。

缓存只保存 ZIP 内部路径等非敏感元数据，不保存以下原值：

- Token
- Cookie
- 客户端证书
- ticket-guard 签名或密钥

### 单行复用

前端在一次 `runBatchDetectionForRow` 中保存账号凭据结果，当前账号和多账号阶段共同复用。该结果只存在于本次函数调用，不进入全局持久缓存。

## 分步耗时

`BatchDetectionRow` 新增结构化步骤耗时，至少包含：

- `localPreparation`
- `token`
- `password`
- `certification`
- `identity`
- `multiAccount`

未执行的步骤不写入耗时。总耗时继续使用现有 `durationMs`。

展示规则：

- 表格“用时”列继续显示总耗时，并在悬浮提示中显示分步耗时。
- 检测详情增加“分步耗时”卡片。
- CSV 在“用时(ms)”后增加“分步耗时”列，使用 `步骤=毫秒` 的稳定文本格式。

耗时只记录阶段边界，不记录 Token、Cookie、证书、URL 查询参数或响应正文。

## 错误处理与状态真实性

- Token 明确失效时才产生掉线信号。
- 超时、HTTP 错误、解析错误和命令异常保留为请求/检测错误，不伪造掉线。
- 一个并行步骤失败时，其他成功步骤仍写回结果。
- 身份补全失败只追加错误，不覆盖 Token 已确认的在线状态。
- 多账号单个账号失败不取消同包其他账号。
- 缓存锁失败时回退为未命中并继续真实扫描，不能阻塞整个包。

## 代码边界

- 新增前端纯模块，负责平衡并发计算、受限并发执行和步骤耗时格式化。
- `App.tsx` 负责编排各阶段、合并现有结果和展示耗时，不改变后端接口响应字段。
- Rust 的 ZIP 文件索引缓存位于现有 `CacheState` 附近，`find_app_file_path` 通过统一缓存入口查询。
- 不在本次把全部检测重写成单个大型 Tauri 命令，也不把阻塞式 `reqwest` 全面改成异步客户端。

## 测试与验证

TypeScript 测试覆盖：

- 不同 CPU 核心数和包数得到 0、少量、6、7、8 路 worker。
- 受限并发执行器不超过给定并发数，并保持结果与输入对应。
- 两个可控延时步骤并行完成，总耗时接近最长步骤。
- 步骤失败不吞掉同阶段的成功结果。
- 分步耗时文本稳定，跳过未执行步骤。
- 工作台源码接入平衡并发、分步耗时和 CSV 新列。

Rust 测试覆盖：

- 相同 ZIP、APP 和后缀查询命中索引缓存。
- ZIP 修改时间变化后使用新缓存键。
- 不同 APP 不共享错误的文件位置。
- 缓存未命中时保持现有 ZIP 查找结果；备份目录绕过缓存并保持现有实时查找结果。

完成前执行：

```bash
npm test
npm run build
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo test --manifest-path src-tauri/Cargo.toml
npm run tauri build -- --bundles app
```

最终重新生成并核对 `src-tauri/target/release/bundle/macos/iOS Sandbox ZIP Reader.app`。没有真实联网样本时，自动测试只能证明调度、缓存、状态合并和打包；实际 200 包耗时仍需要在用户数据上复测。

## 不在本次范围

- 不把 15 秒请求超时缩短到 8–10 秒。
- 不改变 Token 在线/掉线业务判断。
- 不长期缓存敏感参数原值。
- 不实现请求取消或强制终止正在执行的联网请求。
- 不全面重写为异步 Rust 网络架构。
